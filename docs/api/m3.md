# M3 API and signing contract

The M3 server implements:

```text
POST /v1/agents
POST /v1/agents/:agentId/versions
POST /v1/agents/:agentId/versions/:versionId/revoke
POST /v1/experiments
POST /v1/experiments/:experimentId/start
GET  /v1/experiments/:experimentId/policy
GET  /v1/experiments/:experimentId/instruments
GET  /v1/experiments/:experimentId/portfolios
POST /v1/experiments/:experimentId/actions
GET  /v1/experiments/:experimentId/actions/:actionId
```

All bodies use strict schemas from `@poa/schemas`; unknown fields fail. The action endpoint accepts `{ request: { intent, signature, idempotencyKey }, signedBytes }`. `signedBytes` is the lowercase hex encoding of the canonical SDK EIP-712 object. Its message contains `allocationHash = keccak256(POA-CJSON-1(targetAllocation))`. The stored intent, EIP-712 digest and signed bytes each have a separate hash.

The API uses the PostgreSQL clock for `receivedAt`, then writes the accepted request, journal event, scenario active marker and job in one transaction. HTTP 202 acknowledges durable acceptance only. Execution status is read separately. Exact idempotent repeats return the original action and never enqueue another job.

Stable client failures include `INVALID_SCHEMA`, `PAYLOAD_TOO_LARGE`, `DEPENDENCY_UNVERIFIED`, `EXPERIMENT_LOCKED`, `KEY_REVOKED`, `INVALID_SIGNATURE`, `POLICY_VIOLATION`, `EXPIRED`, `STALE_PORTFOLIO`, `NONCE_USED`, `IDEMPOTENCY_CONFLICT`, `SCENARIO_BUSY` and `QUOTA_EXCEEDED`. Internal database details are not returned.

The manifest profiles cannot currently start. The opt-in `synthetic-m3-local` test fixture is described in the [M3 runbook](../runbooks/m3-signed-intent.md).
